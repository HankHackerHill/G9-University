# Testing guide (Stage 03 entry): headless, on the G9 host, and what is not testable yet

Labels used below: **TESTED** (executed here on 2026-11-07, result observed), **INFERRED**, **ASSUMED**, **PROPOSED**, **NOT RUN**.

The backend (`crates/*`) is exercised without the desktop shell through the command-line driver `apps/cli` (binary `g9`). It composes the backend exactly like the Tauri bridge (`apps/desktop/src-tauri/src/lib.rs`): private data directory, binding key file (`g9_app::keyfile`, `0600`, 32 bytes), `Database::open` of `<data>/g9.sqlite`, `AppContext::builder(..).open()` (recovery), backend-assigned operator, `NullRuntime`. Every command goes through `g9_app::dispatch`; the CLI never writes SQL and never sets the actor from input.

### 1.1 The CLI

```sh
G9=target/cli/debug/g9            # after `cargo build` in apps/cli
D=$(mktemp -d)/data               # any directory; default $XDG_DATA_HOME/g9-mentor or ~/.local/share/g9-mentor

$G9 init --data-dir "$D"                                   # creates the layout, runs recovery, prints RecoveryReport + system.status
$G9 import-seed --data-dir "$D"                            # curriculum.validate -> curriculum.import (PROPOSED_SEED) via the approval round trip
$G9 simulate-week --scratch --data-dir "$D" --start-date 2026-11-16 --zone Europe/Berlin --fixed-clock 1794812400000 --human   # --scratch: D must be a throwaway directory
$G9 ops --schemas                                          # the 35 routed operations + the PROPOSED names
$G9 call session.list --data-dir "$D" --payload '{}'       # any operation; --mode/--domain override the UI defaults
$G9 approvals --data-dir "$D" --state PENDING
$G9 approve <approval_id> --data-dir "$D"
$G9 status --data-dir "$D" --human
$G9 restore --backup-id <id> --data-dir "$D"                                      # offline restore: prints the plan, exit 1, changes nothing (§1.6)
$G9 restore --backup-id <id> --data-dir "$D" --confirm-replace-live-database      # replaces the live database; the old one goes to "$D/quarantine"
```

Exit codes: `0` success (JSON on stdout, `--human` for a readable form); `2` the backend refused (the serialized `G9Error`, closed 13-category set) or a scripted scenario did not `PASS` (`INCOMPLETE` or `FAIL`, report on stdout, `g9: scenario <result>` on stderr); `1` usage or host I/O error (stderr), or `g9 restore` without `--confirm-replace-live-database` (the plan on stdout, nothing changed). The binding key is never printed: outputs name `<data>/binding.key` only, and the smoke test and the integration test grep every stdout/stderr capture for the key bytes in hex (both cases), base64 (standard and URL-safe) and Rust byte-list form.

Global flags: `--data-dir`, `--skills-dir` (default `<repo>/.agents/skills` when it exists; 37 packages load in about 65 ms) or `--no-skills`, `--program-start YYYY-MM-DD` (Monday of program week 1, needed by `curriculum.daily_plan` through `g9 call`), `--zone` (default: host zone from `TZ`, `/etc/localtime`, `/etc/timezone`; else UTC with a warning), `--operator-id` (default `local-operator`, the bridge's constant, so one data directory keeps one attributable operator).

### 1.2 The simulated week (Stage 03 exit criterion)

`g9 simulate-week` (which writes seed rows directly to storage and therefore refuses to run without `--scratch`, a usage error with exit 1; see "Scratch guard" below) drives, in order: recovery at open; `curriculum.daily_plan` probe and, when no version exists, `curriculum.validate` → `curriculum.import` (`APPROVAL_REQUIRED` expected) → `approvals.decide` → retry; materialization of one `PLANNED` session per study block for the six days and of the Saturday blind practical (competency, definition, version, baseline rubric); per day `curriculum.daily_plan`, per block `session.prepare` → `session.start` → clock advance by the block minutes (one `session.pause`/`session.resume` on the third block) → `session.complete` with the check *credited time = planned minutes*; `notes.create` (learning journal); on Saturday `assessment.begin` → `submit` → `review_evidence` → `grade_provisional` → `approve_final` (`APPROVAL_REQUIRED` expected) → `approvals.decide` → retry → `APPROVED_FINAL`; `retention.due`, `competency.projection`; `backup.create` → `backup.verify` → `backup.restore_test` (`RETAINED`, integrity `OK`); `audit.recent` and `AuditChain::verify_chain` (chain verifies and has more rows than at open).

TESTED result (2026-11-08, `--fixed-clock 1794812400000`, `--no-skills`): `PASS`, `complete: true`, 193 steps, 0 failures, 0 NOT RUN; 34 block sessions completed with credited = planned; attempt `APPROVED_FINAL` (total 80.0, `SELF_ADJUDICATED`); the final grade is derived into 3 competency observations (understanding, application, transfer; difficulty 3 as declared by the seed) and the last `competency.projection` step lists them in `evidence_refs` (check `competency.projection includes the observations of the finalized attempt`); because the operator grades their own attempt the projection is `provisional` and never `VALIDATED` (check `self-adjudicated grade does not validate (provisional, no VALIDATED)`); backup `RETAINED`; audit rows 0 → 134; the step table of a second fresh run is byte-identical and the two full reports differ only in `data_dir` and `artifacts` (backend uuid-v7 ids: approvals, notes, attempt, backup) — verified by `diff` of the two JSON files.

Verdict: `result` is `PASS` only when every step ran and every check passed (exit 0); `INCOMPLETE` when nothing failed but a step answered `PRECONDITION_FAILED <area>.not_implemented` (`NOT RUN (PROPOSED)`, listed in `not_run`; exit 2 — a partial week is not the exit criterion); `FAIL` otherwise (exit 2). A mutating step whose outcome is `replayed = true` is `FAIL: idempotency.replayed`: the backend returned a stored outcome and executed nothing.

Rules: `--start-date` must be a Monday; `--week N` places it in program week N (program start = start − 7·(N−1) days; an explicit `--program-start` must agree or the command is a usage error). Re-running the same week against the same data directory is `FAIL` at the first mutating step and executes nothing: `FAIL: idempotency.replayed` when the sequential idempotency keys line up with the earlier run (same `--fixed-clock`, seed imported by another process — the smoke test's case), `session.illegal_transition` when they do not (the integration test's case, where the first run's in-process import offsets the counters); both carry a hint (use a fresh `--data-dir` or another `--week`). Steps that have no IPC path yet are written through the typed `g9-storage` repositories and shown as `seed:sessions` / `seed:assessment` with decision `SEEDED` (the same path `g9-evaluation` fixtures use); they are not pipeline outcomes and are the only writes that bypass `dispatch` (confined to `simulate-week` and `crash-drill`; never reachable from `g9 call`; both refuse to run without `--scratch`).

Scratch guard (ADR-0010 addendum, TESTED 2026-11-08): `simulate-week` and `crash-drill` exit 1 with a message that explains that they write seed rows directly to storage and must only be pointed at a throwaway data directory, unless `--scratch` is given; the refusal happens before anything is opened or created (smoke test: exit 1, message, no data directory; unit test `the_seed_writing_commands_refuse_without_scratch_and_create_nothing`; `apps/cli/tests/restore.rs::the_seed_writing_commands_refuse_to_run_without_scratch`). The flag is an explicit acknowledgement; it does not inspect the directory (detecting operator data is PROPOSED).

TESTED through the binary (`apps/cli/tests/simulate_week.rs::crash_drill_then_init_reports_the_interrupted_session_through_the_binary`: one open interval in the drill output, `closed_intervals` equal to that interval, `credited_ms = 0`, no key material in any output) and in the smoke test, which additionally reads `time_intervals` read-only before recovery (exactly one row with `end_utc IS NULL`) and after (none). ### 1.6 Backups across processes and the offline restore (2026-11-08, all TESTED here; NOT RUN on the G9 host)

`backup.create`, `backup.verify` and `backup.restore_test` can run as separate `g9 call` commands: the manifest is read from `backup_manifests` (`g9_storage::backup::read_manifest`), and `system.status.last_backup` is the newest `RETAINED` manifest in the database.

```sh
ID=$($G9 call backup.create --data-dir "$D" --payload '{"label":"manual"}' | python3 -I -c 'import json,sys; print(json.load(sys.stdin)["result"]["backup_id"])')
$G9 call backup.verify       --data-dir "$D" --payload "{\"backup_id\":\"$ID\"}"      # a new process reads the manifest: CHECKED
$G9 call backup.restore_test --data-dir "$D" --payload "{\"backup_id\":\"$ID\"}"      # RETAINED
$G9 status --data-dir "$D"                                                              # result.last_backup names $ID
# stop the application (desktop shell and every g9 process), then:
$G9 restore --backup-id "$ID" --data-dir "$D"                                           # plan; exit 1; nothing changed
$G9 restore --backup-id "$ID" --data-dir "$D" --confirm-replace-live-database          # exit 0; old database in "$D/quarantine"; one line in "$D/restore-log.jsonl"
```

Evidence: `crates/g9-app/tests/backup_persistence.rs` (9 tests: create in one context lifetime, verify and restore-test in the next, status across lifetimes without a warning, unknown id `NOT_FOUND`, `STALE_REVISION` against the stored revision, a second context advancing a backup is seen and never overwritten, the pre-migration backup of a version-9 database restore-tested after a reopen, a recorded path outside the approved roots or a relative path refused before any state changes, a deleted snapshot file fails cleanly to the terminal `FAILED` state, an undecodable row fails closed and `system.status` reports `system.status.last_backup_unreadable`);
