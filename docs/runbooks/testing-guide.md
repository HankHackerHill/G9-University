# Testing guide (Stage 03 entry): headless, on the G9 host, and what is not testable yet

Labels used below: **TESTED** (executed here on 2026-11-07, result observed), **INFERRED**, **ASSUMED**, **PROPOSED**, **NOT RUN**.

The backend (`crates/*`) is exercised without the desktop shell through the command-line driver `apps/cli` (binary `g9`). It composes the backend exactly like the Tauri bridge (`apps/desktop/src-tauri/src/lib.rs`): private data directory, binding key file (`g9_app::keyfile`, `0600`, 32 bytes), `Database::open` of `<data>/g9.sqlite`, `AppContext::builder(..).open()` (recovery), backend-assigned operator, `NullRuntime`. Every command goes through `g9_app::dispatch`; the CLI never writes SQL and never sets the actor from input.

### 1.1 The CLI

```sh
G9=target/cli/debug/g9            # after `cargo build` in apps/cli
D=$(mktemp -d)/data               # any directory; default $XDG_DATA_HOME/g9-mentor or ~/.local/share/g9-mentor

$G9 init --data-dir "$D"                                   # creates the layout, runs recovery, prints RecoveryReport + system.status
$G9 import-seed --data-dir "$D"                            # curriculum.validate -> curriculum.import (PROPOSED_SEED) via the approval round trip
$G9 simulate-week --data-dir "$D" --start-date 2026-11-16 --zone Europe/Berlin --fixed-clock 1794812400000 --human
$G9 ops --schemas                                          # the 35 routed operations + the PROPOSED names
$G9 call session.list --data-dir "$D" --payload '{}'       # any operation; --mode/--domain override the UI defaults
$G9 approvals --data-dir "$D" --state PENDING
$G9 approve <approval_id> --data-dir "$D"
$G9 status --data-dir "$D" --human
```

Exit codes: `0` success (JSON on stdout, `--human` for a readable form); `2` the backend refused (the serialized `G9Error`, closed 13-category set) or a scripted scenario did not `PASS` (`INCOMPLETE` or `FAIL`, report on stdout, `g9: scenario <result>` on stderr); `1` usage or host I/O error (stderr). The binding key is never printed: outputs name `<data>/binding.key` only, and the smoke test and the integration test grep every stdout/stderr capture for the key bytes in hex (both cases), base64 (standard and URL-safe) and Rust byte-list form.

Global flags: `--data-dir`, `--skills-dir` (default `<repo>/.agents/skills` when it exists; 37 packages load in about 65 ms) or `--no-skills`, `--program-start YYYY-MM-DD` (Monday of program week 1, needed by `curriculum.daily_plan` through `g9 call`), `--zone` (default: host zone from `TZ`, `/etc/localtime`, `/etc/timezone`; else UTC with a warning), `--operator-id` (default `local-operator`, the bridge's constant, so one data directory keeps one attributable operator).

### 1.2 The simulated week (Stage 03 exit criterion)

`g9 simulate-week` drives, in order: recovery at open; `curriculum.daily_plan` probe and, when no version exists, `curriculum.validate` → `curriculum.import` (`APPROVAL_REQUIRED` expected) → `approvals.decide` → retry; materialization of one `PLANNED` session per study block for the six days and of the Saturday blind practical (competency, definition, version, baseline rubric); per day `curriculum.daily_plan`, per block `session.prepare` → `session.start` → clock advance by the block minutes (one `session.pause`/`session.resume` on the third block) → `session.complete` with the check *credited time = planned minutes*; `notes.create` (learning journal); on Saturday `assessment.begin` → `submit` → `review_evidence` → `grade_provisional` → `approve_final` (`APPROVAL_REQUIRED` expected) → `approvals.decide` → retry → `APPROVED_FINAL`; `retention.due`, `competency.projection`; `backup.create` → `backup.verify` → `backup.restore_test` (`RETAINED`, integrity `OK`); `audit.recent` and `AuditChain::verify_chain` (chain verifies and has more rows than at open).

TESTED result (2026-11-07, `--fixed-clock 1794812400000`, `--no-skills`): `PASS`, `complete: true`, 191 steps, 0 failures, 0 NOT RUN; 34 block sessions completed with credited = planned; attempt `APPROVED_FINAL` (total 80.0, `SELF_ADJUDICATED`); backup `RETAINED`; audit rows 0 → 134; the step table of a second fresh run is byte-identical and the two full reports differ only in `data_dir` and `artifacts` (backend uuid-v7 ids: approvals, notes, attempt, backup) — verified by `diff` of the two JSON files.

Verdict: `result` is `PASS` only when every step ran and every check passed (exit 0); `INCOMPLETE` when nothing failed but a step answered `PRECONDITION_FAILED <area>.not_implemented` (`NOT RUN (PROPOSED)`, listed in `not_run`; exit 2 — a partial week is not the exit criterion); `FAIL` otherwise (exit 2). A mutating step whose outcome is `replayed = true` is `FAIL: idempotency.replayed`: the backend returned a stored outcome and executed nothing.

Rules: `--start-date` must be a Monday; `--week N` places it in program week N (program start = start − 7·(N−1) days; an explicit `--program-start` must agree or the command is a usage error). Re-running the same week against the same data directory is `FAIL` at the first mutating step and executes nothing: `FAIL: idempotency.replayed` when the sequential idempotency keys line up with the earlier run (same `--fixed-clock`, seed imported by another process — the smoke test's case), `session.illegal_transition` when they do not (the integration test's case, where the first run's in-process import offsets the counters); both carry a hint (use a fresh `--data-dir` or another `--week`). Steps that have no IPC path yet are written through the typed `g9-storage` repositories and shown as `seed:sessions` / `seed:assessment` with decision `SEEDED` (the same path `g9-evaluation` fixtures use); they are not pipeline outcomes and are the only writes that bypass `dispatch` (confined to `simulate-week` and `crash-drill`; never reachable from `g9 call`).

### 1.3 Smoke test (`scripts/smoke_test.sh`)

Builds `g9`, creates a disposable directory and asserts (67 assertions, TESTED 2026-11-07, `SMOKE TEST PASS` in about 9 s after the build): `init` (storage `READY`, model unavailable, egress disabled, chain ok, key file `0600`/32 bytes, fallback warning); `import-seed` (`g9-ct9-480:0.1.0-seed`, 12/72/216, approval consumed; re-run reports `already_imported`); `simulate-week` (`PASS`/`passed`/`complete`, empty `failures` and `not_run`, 34 completions, 6/6/6 daily plans/pauses/notes, `APPROVED_FINAL`, `RETAINED`; two fresh directories give identical step tables and full reports that differ only in `data_dir,artifacts`; the fresh run has exactly 4 more steps than the run with the seed pre-imported; a re-run on the same directory is `FAIL` at `session.prepare` with `FAIL: idempotency.replayed`, completes no session, and only the audit-growth check fails after it); the two-step crash drill (`crash-drill` reports one interval with `end_utc: null`; a read-only SQLite query of `time_intervals` finds exactly one open interval before recovery and none after; `init` reports `recovery.closed_intervals = [that interval]`, `recovery.interrupted_sessions = [that session]`, state `INTERRUPTED`, continuity `UNCERTAIN`, `credited_ms = 0`, `requires_correction = true`, chain ok; a second `init` has nothing left to recover); the refusal that must happen and the decision both ways, each step its own process (`calendar.propose ADD_REVIEWS` → `calendar.apply` without approval → `APPROVAL_REQUIRED`, exit 2, pending request listed; `g9 reject` → `REJECTED`, `--reason` reported as not persisted, re-presenting the rejected approval → `APPROVAL_REQUIRED approval.not_approved`; a second proposal → `g9 approve` → `g9 call calendar.apply --approval` succeeds → the approval is `CONSUMED` → presenting it again is refused); `skills.invoke` (registry loads: `packages > 0`, `refused: null`; `EXAM` with the registry → exactly `PRECONDITION_FAILED skills.preflight_failed`; `--no-skills` → exactly `RESOURCE_UNAVAILABLE skills.registry_unavailable`; allowed mode with the `NullRuntime` → `RESOURCE_UNAVAILABLE skills.backend.unavailable`); a PROPOSED operation (`teaching.propose_hint` → `PRECONDITION_FAILED teaching.not_implemented`); unknown operation (`INVALID_INPUT`); bad JSON and a Tuesday start date (exit 1); `ops` (35); `status` `READY`; no key material in any stdout/stderr (hex, base64, byte list of every `binding.key` created). The step counts are 187 with the seed pre-imported and 191 on a fresh directory.

Observed skill refusals (TESTED): with the 37 packages loaded, `skills.invoke` in `EXAM` mode for `g9-socratic-coaching` (modes STUDY, LAB) answers `PRECONDITION_FAILED skills.preflight_failed` ("mode Exam is not allowed for this skill") from the orchestrator preflight, before any model call; without a registry (`--no-skills`) `RESOURCE_UNAVAILABLE skills.registry_unavailable`; in an allowed mode with the `NullRuntime` `RESOURCE_UNAVAILABLE skills.backend.unavailable`. The policy table itself allows `operator.invoke.allow` in every mode, so the EXAM refusal is a preflight precondition, not an `UNAUTHORIZED` policy denial; the smoke test asserts the observed categories.

### 1.4 Crash drill (two steps)

```sh
$G9 crash-drill --data-dir "$D"    # materializes one PLANNED session, session.prepare + session.start, exits without completing (connection left open)
$G9 init --data-dir "$D"           # recovery: recovery.interrupted_sessions = [<id>], closed_intervals = [<interval>],
                                   # interrupted_sessions[0].state = INTERRUPTED, .intervals[0].continuity = UNCERTAIN, requires_correction = true
```

TESTED through the binary (`apps/cli/tests/simulate_week.rs::crash_drill_then_init_reports_the_interrupted_session_through_the_binary`: one open interval in the drill output, `closed_intervals` equal to that interval, `credited_ms = 0`, no key material in any output) and in the smoke test, which additionally reads `time_intervals` read-only before recovery (exactly one row with `end_utc IS NULL`) and after (none). The drill leaves the WAL uncheckpointed (`g9.sqlite` 4 KiB, `g9.sqlite-wal` about 2 MiB), the shape a killed process leaves. The uncertain time is never credited; `session.correct_time` (operator correction) is the only way to credit it.
