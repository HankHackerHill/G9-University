# ADR-0014: SKILL.md is instructional metadata; permissions are decided in Rust; protected operations get a native confirmation

**Status:** Accepted (2026-11-06)

## Context

v5.1 treated skill metadata as the permission source (C11); auditors added that approvals granted from a compromised webview are forgeable (SEC-03).

## Decision

The registry validates packages and refuses operator-only capability requests at load; the orchestrator never grants capabilities; policy decides per invocation. Complementary control (PROPOSED, Stage 03): protected operations (approval grant, grade finalization, curriculum promotion, schedule apply, export, deletion, policy/model changes) raise a native confirmation dialog from Rust (`tauri-plugin-dialog`, `dialog:allow-confirm` only) whose text is generated by Rust from the typed operation; the webview request is a proposal, the native dialog is the grant.

## Alternatives considered

Trust `allowed-tools` from SKILL.md (rejected). Webview-only PIN (rejected per handoff §12).

## Consequences

Compromised content or webview cannot escalate to protected operations without a native operator action.

## Verification

`a07_requested_operator_only_capability_rejected_at_load`, `a07_output_requesting_execute_is_rejected_at_validation`; dialog wiring NOT RUN until Stage 03.

## Addendum (2026-11-13): native confirmation implemented for approval grants

| Part | Implementation |
|---|---|
| Chokepoint | The approval grant (`approvals.decide` APPROVE). Every protected operation listed above is approval-gated, so none proceeds without a granted approval. |
| Backend | `g9_app::dispatch_confirming` reads what the approval grants from storage (`ApprovalSummary`: operation, resource, revision, request and expiry times; nothing from the payload but the approval id), asks `confirm`, and dispatches only on `true`. A plain `dispatch` of an APPROVE is refused `UNAUTHORIZED approval.native_confirmation_required` while `AppConfig::native_confirmation` is on (the default). REJECT needs no confirmation. |
| Desktop shell | `g9_command` passes a closure that raises a GTK `MessageDialog` (Cancel default, Approve) on the GTK main thread via `AppHandle::run_on_main_thread`, transient for the main window, and waits for the answer; any failure is a refusal. Other platforms answer `false` (fail closed; approve with the CLI there). |
| CLI | Sets `native_confirmation = false`: a terminal surface the operator types into. Whether the CLI stays an approval surface is an open operator decision. |
| Deviation | `tauri-plugin-dialog` is not used: GTK is already in the locked dependency tree (`gtk 0.18.2` through tauri), so no new crate enters the build and nothing is invocable from the webview (no dialog permission exists in the capabilities). The crate host `static.crates.io` was also not reachable from the build sandbox. |

Verification: `crates/g9-app/tests/native_confirmation.rs` (a webview-only grant refused, failing before with the gate off; a declined dialog refused; a confirmed grant with the dialog text read from the stored request; REJECT unconfirmed); shell bridge test `an_approval_without_the_native_dialog_is_refused`; the shell type-checks and passes clippy `-D warnings` (all targets) against placeholder pkg-config metadata. NOT RUN here: the shell's tests (they need the GTK/WebKit libraries to link) and the dialog on a display; run them on the G9 host or in CI started by hand. Still missing for SEC-03: an approval-request rate limit, Tauri's isolation pattern, an app ACL manifest.

## Addendum 2 (2026-11-13, security audit): the confirmation says what the record is

| Part | Implementation |
|---|---|
| Finding | Audit 2026-11-13, A1 (MEDIUM) and A2 (LOW): the dialog showed an operation name and an opaque id, so the operator could not tell the record the page displayed from the record the approval covered; a compromised webview could ask about one record and show another. For `curriculum.import` the text held words chosen by the requester. |
| Text | `ApprovalSummary::text()` (`crates/g9-app/src/dispatch.rs`): one fact per line, every one written by the backend from storage: `Approve`, `What`, `Grants` (the capability policy decided), `Asked in` (area and mode the request was made in, labelled as the request's own context), `Record` (kind, id, revision), `Fingerprint of the exact values` (first 16 hex characters of the parameters hash), request and expiry times, approval id. |
| Subject | `g9_storage::describe::describe_resource` reads the stored row: a note's title, classification, area and number of attached files; a file's name, size and note; an event's title and time; an attempt's assessment and latest grade; a proposal's number of calendar changes; an export's areas, format and whether private records go. A record that is not stored yet says so and is fixed by the fingerprint. |
| Sanitising | Every stored word passes `g9_domain::text::one_line`: control, line-separator, bidirectional, invisible and tag characters become U+FFFD, whitespace runs one space, length capped. A title cannot forge a second line or reorder the first. Titles, file names and labels that are blank or hold such characters are also refused at the boundary (`input.name_not_printable`, `crates/g9-app/tests/names.rs`). |
| Arming delay | "Approve" is inert for 1.5 s after the dialog appears (`APPROVE_ARMS_AFTER` in `apps/desktop/src-tauri/src/lib.rs`): a click or key press already under way when it opens cannot approve text that was not read. |
| NOT RUN | The GTK dialog, its timer and the stacking of two confirmations (the shell cannot be built in the authoring sandbox; it is type-checked and linted only). |

Verification: `crates/g9-app/tests/native_confirmation.rs` (two requests for two notes cannot be confused; stored text cannot forge or reorder a line; a record that is not stored yet is said to be new and the grant is shown; an export says which areas leave; an erasure says how many files go with the note); `crates/g9-storage/src/describe.rs` tests.
